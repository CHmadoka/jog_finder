# 原始数据留存机制(data/raw/)

日期:2026-11-08

## 动机

平台接口/页面结构变化后,排查解析问题(字段缺失、语义不明、风控形态)只能临时
写诊断脚本重新实测平台——既费事又额外暴露请求。本次在"平台响应 → 解析器"边界
增加原始数据落盘:之后排查直接翻 `data/raw/` 文件,不必再针对平台重放测试。

## 机制

- 位置:`data/raw/{平台}/{kind}_{YYYYmmdd_HHMMSS}_{4hex}.json`(utils.save_raw);
- 信封结构:`{ts, platform, kind, meta, body}`——meta 携带词条/城市/页码/URL/取数
  路径(via),body 为**平台原始响应或解码前提取产物**,原样不变形;
- 覆盖点(每平台列表 + 详情两类):

| 平台 | kind | body 内容 |
|---|---|---|
| job51 | search | search-pc 整页响应(首屏捕获 via=first_screen / PV 配平 via=page_pv / 页内 fetch);**非 JSON 响应**单独 kind=search_nonjson(raw_head 截断文本,风控页样本) |
| job51 | detail | 详情兜底的 JSON-LD 原文数组 + 解析后字段 |
| boss | search | joblist.json 完整响应(含拒绝码形态,code=31 403 页实测已自动留档) |
| boss | detail | evaluate 原始产物 + **字形解码映射 decodeMap**(解码前,薪资乱码排查关键) |
| liepin | search | pc-search-job 完整响应(flag≠1 拒绝形态同 kind 留存) |
| liepin | detail | JSON-LD 原文数组 + 解析结果 |

- 拒绝/异常形态与成功响应同 kind(body 自带 status/code/flag 可辨);
- 量控(.env 可调,默认开启):`RAW_CAPTURE`(0=关闭)、`RAW_RETENTION_DAYS=7`
  (按 mtime 过期清理)、`RAW_MAX_PER_PLATFORM=300`(超限删最旧);每次写入后顺手
  清理,单平台文件量小,成本可忽略;
- 落盘全程 try/except 包裹,失败仅 warning,**绝不影响抓取主流程**;
- 零 DB schema 变更:留存是文件级旁路,不进库、不参与任何判定。

## 使用

排查示例:字段语义疑问(如 HR 活跃分档)→ 打开最近一份 `job51/search_*.json`
按 meta.keyword 定位,直接核对 body 字段;接口改版 → 对比新旧两份 body 的键集;
风控误判 → 看 search_nonjson / 拒绝码 body 的实际形态。配合
`scripts/diag_hr51.py` 等诊断脚本做主动重放,常规排查不再需要打开平台页面。

## 验证

- 单测 107 全过(新增 `tests/test_save_raw.py` 5 个:信封结构/开关/序列化兜底/
  数量上限清理/过期清理);
- 实测三平台:test_live job51(首屏路径,183KB 完整响应)、boss(登录探测即落盘,
  自动留档 code=31 403 形态)、liepin(响应捕获路径,82KB)。
