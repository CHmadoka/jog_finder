# 2026-11-06 修复说明:旧数据修复(HR 活跃补全)功能

## 背景

库内 28 条岗位中 11 条(早期版本入库)`hr_active_at` 为空,界面 HR 活跃显示 "-"。
已入库岗位在正常抓取流程中会被"详情前查重"跳过、不再打开详情页,活跃字段永远不会被补上,
因此需要独立的旧数据修复能力。

## 新增:补全任务(API + 前端入口)

- **API**:`POST /api/tasks/refresh_active`,body `{platform}`,与抓取任务共用
  "每平台仅一个任务"互斥;进度实时显示在左栏状态区(前缀 `[补全]`),不产生 crawl_task 记录。
- **前端**:顶栏菜单新增「补全HR活跃(旧数据修复)」。
- **流程**(`scheduler/runner.py`):
  1. `_db_load_missing_active` 取该平台活跃字段为空的岗位;
  2. 逐条构造 `JobDraft` 复用平台 `_parse_detail` 打开详情解析(自动携带节流抖动、
     防 securityId 重定向参数、免疫补丁);
  3. `_db_refresh_job_active` 回写:仅补空/有变化字段(活跃时间、活跃原文、空描述、
     open_params),不覆盖已有数据;
  4. 落地 jobId 不匹配(平台重定向到其它岗位)按"已下线"跳过,页面被反自动化清空
     按"拦截"跳过,均写入异常面板;
  5. 结束后进度区显示"补全完成:更新 N,未获取 M"。
- **平台钩子**:`base.py` 新增 `rebuild_open_params(page, jid2kw)`(默认恒等实现);
  Boss 覆写为"经列表接口重建 securityId/lid"备用。本轮实测列表接口降级只回 15 条,
  旧岗位多不在列表,故主流程直接裸直链打开(实测可正常按 jobId 落地),校验兜底。

## 顺带修复的问题

1. **冷启动"浏览器在连接后退出"**(root cause 闭环):
   `_launch` 首屏固定 `about:blank` → 注入免疫补丁(原生 CDP) → 原生导航到目标页。
   之前直接以平台页为首屏时,文档创建早于注入,首屏必然经历一段无补丁裸奔窗口,
   反调试命中即 `window.close()` 偷关唯一标签 → 整个浏览器退出。
2. **页面关闭看门狗**:已加载页面被偷关时自动重开同 URL 载体页(5s 去重),
   确保浏览器始终至少有一个平台标签。
3. **安全验证误报**:`_is_verify_page` 原来对 title+全文做"验证码/安全验证"子串匹配,
   正常岗位详情(如 AI 公司描述里出现"验证码")会误判。改为 URL 特征优先;
   文本特征要求正文足够短(<800 字符,真验证页只有标题+滑块)。
4. **验证页标签保留**:判定从 URL 改为页面内容检测(验证页只替换内容不改 URL),
   `iter_jobs` 与补全任务的 finally 均保留验证页标签供人工滑块后自动回跳。
5. **服务文件日志**:日志同时写入 `data/app.log`(控制台窗口 + 文件双输出),
   服务窗口被误关后日志仍可查。

## 验证结果

  未获取 2(详情页正常但平台未提供活跃文案,#25/#26)。
- 全库活跃覆盖:15 有 / 11 空 → **24 有 / 2 空**。
- "3日内活跃"变体由本轮补充的 `_ACT_RE` 规则命中。
- 单元测试 46 项全部通过。
