# 风控升级报告:从"速率伪装"到"会话形状伪装"

日期:2026-11-08
范围:Boss直聘 / 猎聘 / 前程无忧 三平台抓取链路的风控对策全面评审与升级路线。

---

## 一、结论摘要(TL;DR)

**"随机等待时间"只伪装了六个可观测维度里的一个(速率),而平台风控判定的是会话形状。
真人高频不触发、自动化低频也被抓的根本原因是:双方在服务器视角下的"会话形状"完全不同,
速率上的随机化救不了一个形状错误的会话。**

| 视角 | 真人(哪怕刷得很快) | 当前自动化(哪怕每次都随机等 3~8 秒) |
|---|---|---|
| 请求速率 | 有快有慢,但**分布是重尾的**(突发+长尾) | uniform(3,8) **平顶均匀分布**——本身就是非人签名 |
| 请求构成 | API 请求是页面浏览的**副产品**,伴随大量埋点/beacon 噪声 | 载体页静止,**纯 API 会话**:PV≈0~1 但接口调用数百次,零噪声 |
| 导航链 | 每个详情页都有完整 referer 链(列表→点击→详情) | 详情页 `page.goto` 直链,新标签**无 referer**,100% 直达入口 |
| 行为语义 | 停留时间∝内容长度;非线性浏览、回访、换词重搜 | 按列表**顺序穷举**详情;按词条×城市**笛卡尔积遍历**;停留与内容无关 |
| 账户基线 | 日活跃量平稳,偶发高峰也在历史分位内 | 单会话请求量是账号历史基线的**几十上百倍** |
| 时段分布 | 昼夜节律,集中在少数时段 | 任意时刻启动,长时间恒定强度 |

当前防线的真实水平:**速率层已经做得很好**(全局闸/批次休息/预热/冷却/静默重试全套齐备),
但**分布层、语义层、结构层基本为零**。这就是"效率太低"的准确含义——不是做得不够多,
而是做在了风控权重最低的维度上。

---

## 二、回答核心问题:为什么真人高频不触发,自动化随机等待也被抓

### 2.1 风控的判定范式:会话形状,而非单点频率

现代招聘平台风控(Boss 的 kanzhun 自研风控、猎聘接入的第三方设备指纹/行为验真、
前程无忧的 Access Verification)的本质是一套**统计判别系统**:把每个会话(session,
以登录态 cookie + 设备指纹 + IP 为标识)表示为一个特征向量,与"该账号自己的历史
基线"和"全体真人用户的分布"比较,偏离即打分,分数过阈值 → 软风控(空列表/签名拒绝/
验证页),再犯 → 硬风控(403 code=32 限流/短信验证)。

单次请求的间隔时间只是特征向量里的**一个分量**,且权重并不高——因为真人刷得快时
间隔也可以低于 1 秒,风控不可能用"间隔小"直接判负。真正有区分度的分量是下面六类。

### 2.2 六类可观测信号(风控实际在看的)

1. **时序分布形状**:真人操作间隔是重尾分布(近似对数正态/伽马):大量 0.5~2 秒的
   快速连击 + 少量 30~120 秒的离开(看手机/倒水/读长描述),且停留时长与页面内容
   长度正相关。`random.uniform(lo, hi)` 产出的是**平顶直方图**,KS 检验/熵检验
   一测即中;`SessionPacer` 固定批长(每 2~4 页、每 8~15 详情)又叠加了一层
   **可统计的元周期**。均匀随机不仅不是伪装,反而是一份"我是均匀分布采样器"的自白。
2. **请求构成(PV:API 比 + 噪声伴随)**:真人一次浏览会产生完整事件链——
   HTML+子资源加载、曝光/点击/停留埋点上报、A/B 配置拉取等几十个请求,
   业务 API 只是副产品。当前 Boss/51job 的"载体页静止 + 页内 fetch"模式,
   服务器看到的是:**PV 几乎为零,业务 API 数百次,且没有任何埋点噪声伴随**。
   这是真人分布里**不存在**的会话形状——与速率无关,低频也判异。
3. **导航链完整性**:真人打开详情页的 referer 是搜索列表页,URL 带点击上下文;
   自动化的详情页是 `page.goto(直链)`,新标签 referer 为空(或 about:blank)。
   "详情页 100% 直达入口、0% 站内来路"是强签名。当前仅 `open_url_native`
   (人工"打开原始页"场景)带了 referrer,三个平台的批量抓取详情全部裸奔。
4. **行为语义**:
   - 详情按列表顺序逐条打开(真人非线性、有回访、有跳过);
   - 词条×城市**有序笛卡尔积**遍历(`runner.py` 的 combos 生成顺序固定);
   - `human_scroll` 的 wheel 事件**之前没有任何 mousemove 轨迹**(受信事件但无轨迹历史);
   - `human_type` 用 Control+A 全选输入(真人极少模式);
   - 停留时间与描述长度完全无关。
5. **账户基线偏离**:风控对每个账号维护历史画像(日均 PV、时段分布、常用功能)。
   一个平时日览 10 个岗位的账号,某天单会话请求 500+ 次——不管间隔多随机,
   偏离度都是满分。这解释了"前 100 条没事,越往后越容易触发"的实测现象
   (Boss 800+ 条后 403 code=32,见 docs/2026-11-07-访问受限立即中断与停止状态修复.md)。
6. **环境与自动化痕迹**(已大幅缓解但非为零):
   - ✅ 已做:真实浏览器 CDP 接管、持久 profile、直连、console noop 免疫、
     `no_defaults=True` 规避 hasFocus 异常——这是项目至今"能跑"的基础;
   - ⚠️ 残留:CDP 域启用序列(Runtime.enable/Page.enable)、`Input.dispatch*`
     产生的无轨迹受信事件、`addScriptToEvaluateOnNewDocument` 的注入痕迹。

### 2.3 软风控的反馈闭环:风险分是累积的

平台不是"每次独立抽签":触发过一次滑块/空列表,账号风险分上调,后续阈值更低、
观察更严。所以:
- 每次触发本身就是"损失",不触发 ≠ 无损;
- "验证通过后立即恢复高频"必然二次触发(代码里 20~40s 冷却的注释方向正确,
  但 20~40 秒远远不够——刚通过验证的会话处于平台重点观察期,应该降档运行数小时);
- 当前策略在"触发后"没有降档机制(只有一次性冷却),风险分只升不降。

## 三、当前防线盘点(截至本次评审)

### 3.1 已落地且方向正确的(保留)

| 防线 | 位置 | 评价 |
|---|---|---|
| 真实浏览器 CDP 接管 + 持久 profile + `--no-proxy-server` 直连 | `app/browser/manager.py` | 环境指纹层最大 correctly-done;headless/伪装浏览器方案全被这里秒杀 |
| console noop 反调试免疫 + `no_defaults=True` | `manager.py` ANTIDEBUG_NEUTRALIZE_JS | 针对实测自杀式反调试,有效 |
| 任务级随机间隔 3~8s(翻页/详情/组合间统一) | `app/utils.py` human_delay/detail_delay | 速率层基础,但**分布形状错**(见 §4) |
| 会话批次长休息 SessionPacer(翻页 2~4 页/详情 8~15 个 → 15~40s) | `base.py` + `utils.py` | 方向对(真人会离开),实现有元周期问题 |
| 跨平台全局导航闸 1.5~3s | `utils.py` global_nav_gate | 解决同 IP 多平台叠加,必要 |
| 任务启动预热(静默停留+轻滚动) | `utils.py` warmup | 消除启动尖峰,对 |
| 验证等待 + 通过后冷却 20~40s | boss/job51 `_wait_manual_verify`/`_wait_if_verify` | 对,但冷却量级偏小 |
| 详情前查重跳过 + 薪资列表期过滤(少开详情) | 三平台 iter_jobs + `runner.py` existing_ids | 减暴露面,对 |
| 拒绝码绝不连发重试 + 静默观察重试(不刷新)+ 3 次中止 | `utils.py` patient_call/patient_poll/silent_backoff | 反连发设计正确,是"不火上浇油"的关键 |
| 受限页(403 code=32)立即中止 | `boss.py` _raise_if_restricted | 正确(实测教训) |
| Boss 载体页静止 + 页内 fetch(避免搜索页自身轮询叠加) | `boss.py` iter_jobs | 降低了**速率**,但制造了**纯 API 会话**(见 §4 结构性问题) |

### 3.2 关键空白(风控权重高但完全未覆盖)

1. **分布形状**:所有间隔 uniform 采样;Pacer 批长/休息亦 uniform。
2. **详情页 referer 链**:三平台 `_parse_detail` 的 goto 均无 referrer。
3. **详情页阅读仿真**:落地即抽 DOM,停留与内容无关,零滚动。
4. **遍历语义**:combos 有序笛卡尔积;列表内详情顺序打开。
5. **会话预算**:无单会话请求上限(仅 max_pages×每页条数,实际可达数百上千)。
6. **时段窗口与节律**:无定时调度,任意时刻可启动长时间恒定强度任务。
7. **风险分降档**:触发风控后无"当日降量/次日恢复"机制,events 表数据未反哺节奏参数。
8. **噪声流量**:零埋点伴随、零站内闲逛行为。

## 四、差距矩阵(信号 × 现状)

| # | 信号维度 | 风控权重(经验) | 现状 | 判定 |
|---|---|---|---|---|
| 1 | 请求速率/全局并发 | 中 | 闸+随机间隔+批次休息 | ✅ 已覆盖 |
| 2 | 时序分布形状 | 中高 | uniform 平顶 + 固定批长元周期 | ❌ 空白 |
| 3 | PV:API 比 / 噪声伴随 | **高** | 纯 API 会话(Boss/51job) | ❌ **结构性缺陷** |
| 4 | referer/导航链 | 高 | 详情页 100% 直达 | ❌ 空白 |
| 5 | 行为语义(顺序/停留/轨迹) | 高 | 顺序穷举、零轨迹、零阅读 | ❌ 空白 |
| 6 | 账户基线偏离 / 会话总量 | **高** | 无预算,单会话可达千级请求 | ❌ **结构性缺陷** |
| 7 | 时段节律 | 中 | 无窗口控制 | ❌ 空白 |
| 8 | 环境指纹/CDP 痕迹 | 中高 | 真实浏览器+console 免疫 | ⚠ 部分覆盖 |
| 9 | 触发后风险分管理 | 中高 | 仅一次性冷却 20~40s | ❌ 空白 |

**结论:两个"结构性缺陷"(纯 API 会话、无会话预算)不是调参数能解决的,
需要行为层改动;这也正是"随机等待无效"的直接答案——被检测的不是"快",
是"形状"。**

## 五、风控升级路线图

### L1 会话形状修复(高收益/低成本,建议本周落地)

| # | 改动 | 要点 | 涉及 |
|---|---|---|---|
| L1-1 | **详情页 referer 链** | `_parse_detail` 的 goto 带 `referrer=搜索列表 URL`(Boss 额外 `transitionType=link` 对齐 `open_url_native` 已有做法) | boss/liepin/job51 `_parse_detail` |
| L1-2 | **对数正态间隔** | human_delay/detail_delay 改 lognormal 采样(μ/σ 由 lo/hi 推导,σ≈0.5),硬下限 lo;~8% 概率长尾(20~90s)、~5% 概率 2 连快击(0.8~1.5s) | `utils.py` |
| L1-3 | **详情页阅读仿真** | 停留时长 ∝ f(描述长度)(lognormal,8~60s 封顶),落地后 human_scroll 2~4 次(先 mousemove 轨迹)再离开 | 三平台 `_parse_detail` + `utils.human_scroll` |
| L1-4 | **打乱遍历** | combos shuffle;列表内详情打开顺序随机抽样(而非顺序全量);偶发"返回列表"节奏 | `runner.py` + 三平台 iter_jobs |
| L1-5 | **会话预算** | 每任务设请求预算(建议初始:Boss 详情≤120、Boss 列表页≤40、51job API≤300、猎聘详情≤100),达限即收尾写摘要;超量需求留给下次任务 | `config.py` + `runner.py` + 三平台 |
| L1-6 | **Pacer 去周期化** | 批长改泊松/几何分布采样,休息时长改对数正态,消除固定元周期 | `utils.SessionPacer` |

### L2 会话仿真(中成本,验证 L1 效果后推进)

| # | 改动 | 要点 |
|---|---|---|
| L2-1 | **API 会话 PV 配平** | Boss/51job 每抓 N(3~6 随机)个接口页,真实导航一次搜索页(产生 PV+平台自身埋点噪声);载体页连续复用超 30~60 分钟换新 PV |
| L2-2 | **事件轨迹仿真** | 统一 `human_act` 工具:wheel/click 前 dispatch 5~10 个贝塞尔插值 mousemove(速度曲线平滑);`human_type` 弃用 Control+A,改三击选中 |
| L2-3 | **噪声闲逛流量** | 任务间隙低频穿插站内真实浏览(首页/公司页/随机岗位),制造埋点伴随 |
| L2-4 | **触发后降档** | events 表按平台统计当日触发次数:1 次 → 当日预算减半;≥2 次 → 该平台冷却 48h;任务启动时读取并自动套用 |

### L3 账户与资源层(高成本,长期)

| # | 改动 | 要点 |
|---|---|---|
| L3-1 | **时段窗口调度** | 任务仅允许人类活跃时段(如 9-12/14-18/20-22),启动时刻随机抖动;夜间自动排队 |
| L3-2 | **多 profile/多账号 + 出口隔离** | 每平台 2~3 个独立 profile 轮换,各绑定固定住宅出口;新 profile 低量预热 2~3 天建立基线 |
| L3-3 | **混合采集(降维打击)** | Boss 列表走 API(便宜),详情只对"筛选入选"的少量岗位打开——暴露面降一个数量级;51job 已天然接近此形态 |

### 度量与验证(证明升级有效,而不是感觉有效)

- **核心 KPI:RBI(Rounds Between Incidents)**= 每次风控事件(验证/受限/空列表)前
  成功完成的请求数,按平台从 events 表 + 任务计数统计;
- 每次 L1 改动上线后做同量级 A/B(旧策略 vs 新策略各跑一轮等量任务),对比 RBI;
- **阈值标定**:逐步上调 L1-5 会话预算,找到各平台触发阈值(如 Boss 详情 403 前的
  详情数),把日常运行参数钉在阈值的 60~70%;
- 现成基础设施:events 表(`_db_add_events`)+ 任务计数(counters)+ 异常面板,
  只需在报告页加一张"近 7 天各平台触发事件 × 当日请求量"的透视即可起步。

## 六、最小改动 Top5(若只做五件事)

1. L1-1 详情页 referer 链(约 1 小时,直接消除最强签名之一);
2. L1-2 lognormal 间隔替换 uniform(约 0.5 小时,消除平顶分布);
3. L1-3 详情页阅读仿真(约 1 小时,把"零阅读访问"变成"有阅读访问");
4. L1-5 会话预算(约 1 小时,砍掉基线偏离这个最大风险源);
5. L2-4 触发后降档(约 1 小时,让风险分可降)。

## 七、风险与权衡

- L1-3/L2-3 会**显著拉长单任务耗时**(吞吐换存活):需与用户明确"抓得更慢但更稳"
  的定位,预算参数做成 `.env`/前端可调;
- L2-1 的 PV 配平会增加总请求数(多出的 PV),需要实测确认净收益为正;
- L3-2 多账号涉及账号合规风险,由用户自行评估;
- 所有改动保持现有"拒绝码不连发/受限即中止/静默重试"防线不变——它们是止损网,
  不是伪装层,两层互补不可偏废。
